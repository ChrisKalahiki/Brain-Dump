# Brain-Dump v2 spec

Terms are defined in [`GLOSSARY.md`](../../GLOSSARY.md). Every decision links to the ticket that holds its detail on the [Brain-Dump v2 map](https://github.com/ChrisKalahiki/Brain-Dump/issues/29). Tracked as [#55](https://github.com/ChrisKalahiki/Brain-Dump/issues/55).

## Problem Statement

Brain-Dump v1 gets Items out of AI Sessions and into the Vault, but only when the user remembers to run `dump`, and only one way: writes. Five gaps remain.

- **Weak safety.** Every write rests on a skill behaving well. Nothing in the helper proves an approved Filing Plan lost no curated text. An agent can still edit or read the Vault directly with its native tools. A bad Run can't be undone. A note can change between the user reading a Filing Plan and saying `ok`.
- **Write-only.** Nothing that was filed comes back. A new Session in a repo starts blind to the Decisions, Learnings and Todos the Vault already holds for that project, so things get re-decided.
- **Memory-dependent capture.** Sessions the user never dumped are lost once the tools delete their logs, which Claude Code does after 30 days.
- **No maintenance.** Topic Notes and Project Notes only grow. Broken backlinks, dead Routes, stale Dumps and duplicate Items pile up unseen.
- **Fatiguing Filing.** Every Item gets the same full review, even when a Route already says where it goes, and near-duplicates of Items already filed slip through.

Append-only stays absolute ([ADR 0003](../adr/0003-append-only-stays-absolute.md)): v2 adds text and never rewrites or removes curated text.

## Solution

v2 adds a **safety layer first**, then a read side, automated capture and maintenance. All of it sits on the `brain-dump` helper, which keeps owning every Vault read and write ([ADR 0002](../adr/0002-helper-cli-owns-vault-io.md)).

1. **Safety layer.**
   - One write gateway checks every write against the Inbox and Curated Note rules and an independent append-only check, all or nothing ([ADR 0004](../adr/0004-inbox-and-curated-notes.md), [ADR 0005](../adr/0005-one-write-gateway.md)).
   - Every Run is journaled and can be undone exactly ([ADR 0006](../adr/0006-undo-restores-exactly.md)).
   - Plans carry content hashes, so a stale plan is refused.
   - A Vault guard hook stops agents reaching the Vault except through `brain-dump`.
2. **Read side.**
   - A `recall` skill and `recall`/`show` commands answer questions about the Vault from inside any Session ([ADR 0007](../adr/0007-agents-read-through-the-helper.md)).
   - A SessionStart pointer hook names the Vault notes for the current repo in at most three lines.
3. **`check`.** A read-only report of seven kinds of Vault problems, each with its fix.
4. **Consolidation.**
   - A `/consolidate [[note]]` skill adds a cumulative Digest callout to the end of a long note, after the user approves its full text ([ADR 0008](../adr/0008-digest-is-a-cumulative-callout.md)).
5. **Approval tiers.**
   - Routine Items, those whose destination comes from a Route to something that already exists, show compactly in the Filing Plan.
   - They still need an `ok`, and the helper verifies each claimed Route.
6. **Sweep.**
   - A daily per-machine timer drafts one Dump per recent uncaptured Session into the Inbox, through a tool-less agent ([ADR 0009](../adr/0009-the-sweep-calls-the-agent.md)).
7. **Duplicate detection.** The Filing Plan marks Items that nearly duplicate something already in the Vault.
8. **Prompt evals.** Any change to a prompt is scored against committed fixtures before it ships.

## User Stories

### Write gateway and append-only

1. As the Vault owner, I want automation to only ever create new Dump files in the Inbox, so that nothing unattended can touch my Curated Notes.
2. As the Vault owner, I want every change to a Curated Note to come only from a plan I approved, so that I stay in control of my second brain.
3. As the Vault owner, I want Brain-Dump's writes limited to a fixed, code-defined allowlist of folder trees, so that private folders (Journal, templates, `.obsidian`) are never written.
4. As the Vault owner, I want no agent to be able to widen the allowlist by editing a note, so that safety can't be steered from inside the Vault.
5. As the Vault owner, I want a plan that touches more than 8 notes to need a separate, explicit yes, so that a runaway plan can't sweep across the Vault on one `ok`.
6. As the Vault owner, I want the helper to prove every original line of every note it writes still exists in order, so that append-only is enforced, not trusted.
7. As the Vault owner, I want the append-only check to be independent of the code that makes the edits, so that one bug can't both break a note and approve the break.
8. As the Vault owner, I want only empty placeholder bullets to be allowed to disappear, so that filling a template doesn't count as loss.
9. As the Vault owner, I want a Dump being filed to change only its planned Items' checkboxes, so that the record of what I captured stays exact.
10. As the Vault owner, I want a finished Dump moved to `Inbox/Filed/` only when the destination doesn't exist and with exactly the verified contents, so that backlinks keep resolving and nothing is clobbered.
11. As the Vault owner, I want new files created only when nothing exists at that path, so that a create can never overwrite.
12. As the Vault owner, I want a failing check to abort the whole plan with nothing written, so that I never end up with a half-applied Filing.
13. As the Vault owner, I want the error to name the note and the first lost or changed line and call it a `brain-dump` bug, so that I know it's the tool's fault and where to look.
14. As a developer, I want no override flag on the append-only check, so that "just this once" can't become a habit.

### Runs and undo

15. As the Vault owner, I want every set of Vault changes Brain-Dump applies together recorded as one Run, so that I can see and reverse what happened.
16. As the Vault owner, I want `brain-dump runs` to list the 20 latest Runs with time, command, label, file count and status, so that I can find the one I want.
17. As the Vault owner, I want `brain-dump undo <run-id>` to show what it would do before doing anything, so that I can check before reverting.
18. As the Vault owner, I want `undo --confirm` to restore every file the Run touched to its exact prior bytes, delete files it created, and move moved files back, so that undo is exact.
19. As the Vault owner, I want undo refused, naming each file, when any file changed after the Run, so that undo never destroys later work.
20. As the Vault owner, I want the refusal to say "undo run `<id>` first" when a later local Run caused the change, so that I know how to unwind in order.
21. As the Vault owner, I want undoing an undo to work as redo, so that a mistaken undo is recoverable.
22. As the Vault owner, I want a Run that crashed partway to stay undoable, so that a crash never leaves the Vault in a state I can't reverse.
23. As the Vault owner, I want Runs kept for 90 days and then pruned automatically, so that the run store doesn't grow forever.
24. As the Vault owner using two machines, I want undo refused when the Run's Vault path isn't the current Vault, so that one machine's history can't be applied to the wrong Vault.
25. As the Vault owner, I want to say "undo the last Filing" and have the skill find the Run id for me, so that I don't need to copy ids.

### Stale-plan detection

26. As the Vault owner, I want a plan refused when any note it writes changed after the agent read it, so that what I approved is what gets written.
27. As the Vault owner, I want a note edited in Obsidian or changed through Sync to count as changed, so that concurrent edits from my other machine are caught.
28. As the Vault owner, I want a refused plan rebuilt and shown again, headed with the note that changed, keeping my earlier redirects, drops and edits where they still apply, so that I don't repeat myself.
29. As the Vault owner filing several Dumps in one run, I want the plans after the first to stay valid against Brain-Dump's own writes, so that my own Filing doesn't trigger stale errors.
30. As a developer, I want `apply` to refuse any plan that writes an existing file without an `expect` hash for it, so that a skill can't skip the check by omission.

### Vault guard

31. As the Vault owner, I want Claude Code's file tools (edit and read) denied on any path inside the Vault, so that agents can't bypass the helper.
32. As the Vault owner, I want symlinked or relative paths into the Vault resolved before the check, so that path tricks don't slip through.
33. As the Vault owner, I want any Bash call that touches the Vault allowed only when it is a single `brain-dump` invocation, so that agents use the helper and nothing else.
34. As an agent, I want the deny reason to tell me Vault access goes through `brain-dump` (recall, show, write-dump, file), so that I can correct course.
35. As the Vault owner, I want the guard to stand down in a Session I started inside the Vault, so that my own deliberate editing isn't blocked.
36. As the Vault owner, I want the guard to deny when it errors on a call that plausibly touches the Vault, and allow otherwise, so that a bug neither opens the Vault nor breaks unrelated work.
37. As the Vault owner, I want `install.sh` to ask before installing the guard and to say how to remove it, so that I choose what runs in every Session.
38. As a Codex user, I want a best-effort guard adapter that reads `apply_patch` patch text, including patches sent inside Bash heredocs, so that Codex is guarded too.
39. As a Codex user, I want to be told the guard needs a one-time `/hooks` trust step, so that I don't think it's working when it isn't.

### Recall and show

40. As a developer starting work in a repo, I want my agent to look up what the Vault holds about this project, so that it doesn't re-decide settled questions.
41. As an agent, I want `brain-dump recall <terms…>` to return matching Items ranked by hits then recency, so that I find relevant past work.
42. As an agent, I want `recall --project [name]` to return this project's Items newest first, with the current repo as the default, so that I get project context in one call.
43. As an agent, I want `recall --links "[[Note]]"` to return what links to a note, so that I can follow backlinks without Obsidian running.
44. As an agent, I want every result to name its Dump and that Dump's Session origin, so that I know where an Item came from.
45. As an agent, I want results capped at 20 with a count of the rest, so that recall doesn't flood my context.
46. As an agent, I want Items still in the Inbox marked `unfiled` and dropped Items excluded, so that I know what's settled.
47. As an agent, I want `brain-dump show <note>` to return the latest Digest and everything after it, so that I read a long note cheaply.
48. As an agent, I want `show --full` for the whole note, so that I can read everything when I must.
49. As the Vault owner, I want recall scoped to the write allowlist, so that private folders never enter model context.
50. As the Vault owner, I want agents allowed to invoke the `recall` skill on their own, while `dump` and `file` stay manual, so that recall happens when it helps.
51. As a developer using worktrees, I want a project identified by its main worktree's root name, so that worktrees don't split a project.

### Pointer hook

52. As a developer opening a Session in a repo, I want one line naming up to three Vault notes for this project and how many of its Dumps are unfiled, so that I know the Vault has context.
53. As a developer, I want a project matched to notes by its Route first, then by notes holding Items from this project's Dumps, so that the pointer is accurate without guessing.
54. As a developer, I want one line when `check` has findings and one when the last Sweep wrote something or hit a problem in the last 24 hours, so that maintenance surfaces without nagging.
55. As a developer, I want no output at all when there is nothing to say, so that the hook stays quiet in unrelated repos.
56. As a developer, I want the hook to finish within about a second and skip whatever doesn't fit, so that it never slows Session start.
57. As a Claude Code and Codex user, I want the pointer installed in both tools without overwriting my existing hook entries, so that installing Brain-Dump is safe.

### check

58. As the Vault owner, I want `brain-dump check` to report broken backlinks, dead Routes, stale Dumps, stuck Dumps, oversized notes, duplicate Items and malformed Dumps, so that I see what needs care.
59. As the Vault owner, I want every finding to name its fix, so that I know what to do next.
60. As the Vault owner, I want `check` never to write anything, so that I can run it anywhere, any time.
61. As the Vault owner, I want a Dump with unfiled Items more than 14 days old flagged, so that captures don't rot in the Inbox.
62. As the Vault owner, I want a Topic Note or Project Note with 40 or more filed Items since its latest Digest flagged, with `/consolidate [[note]]` as the fix, so that I know when to consolidate.
63. As an agent, I want `check --json` and exit codes 0, 1 and 2, so that I can act on findings programmatically.
64. As the Vault owner, I want `file` to show a one-line `check` summary before it starts, so that I see problems at the moment I'm tending the Vault.

### Consolidation

65. As the Vault owner, I want `/consolidate [[note]]` to draft a Digest of a long Topic Note or Project Note, so that its many Items become readable again.
66. As the Vault owner, I want the Digest added at the end of the note as a `[!summary]` callout with a block ID, and nothing existing changed, so that Consolidation stays append-only.
67. As the Vault owner, I want each Digest to distil the previous Digest plus everything after it, hand-written text included, so that the latest Digest is all I need to read.
68. As the Vault owner, I want each Digest bullet to link to the Dumps its Items came from, and hand-written material marked `(hand-added)`, so that provenance survives summarising.
69. As the Vault owner, I want Decisions that still hold kept with a one-line Why, and contradictions flagged, so that the Digest is honest.
70. As the Vault owner, I want to see and approve the full Digest text, with `ok`, `edit` and `cancel`, so that nothing is summarised behind my back.
71. As the Vault owner, I want Weekly Notes refused and Consolidation never automatic, so that it only happens where and when I choose.
72. As the Vault owner, I want `file` to offer `/consolidate` in one line for any note its `check` flagged as oversized, so that I'm reminded at the right moment.

### Approval tiers

73. As the Vault owner, I want Items whose destination comes from a Route to an existing note or Todo Group listed compactly as `Routine (N)`, so that I review what's new and skim what's known.
74. As the Vault owner, I want anything NEW (note, group, tag, Weekly Note) always in the full table, so that new structure never hides in the compact list.
75. As the Vault owner, I want an `ok` still required even when every Item is routine, so that nothing is written unseen.
76. As the Vault owner, I want redirecting or editing a routine Item to move it to the full table, so that my changes stay visible.
77. As the Vault owner, I want the helper to refuse a plan whose claimed Route doesn't exist or doesn't point where the Item goes, so that a skill can't mislabel an Item as routine.

### Sweep

78. As a developer, I want Sessions I never dumped drafted into Dumps automatically each day, so that nothing is lost before the tools delete their logs.
79. As the Vault owner, I want swept Dumps written only as new files in the Inbox and tagged `dump/swept`, so that I review them through normal Filing.
80. As a developer, I want each Session drafted by its own tool-less, unsaved agent run, so that one bad Session can't affect the others and the Sweep leaves no transcripts of its own.
81. As a developer, I want Sessions already covered by a Dump skipped, and a resumed Session drafted only from where its last Dump stopped, so that nothing is captured twice.
82. As a developer, I want Sessions inside the Vault, subagent threads, short Sessions, active Sessions and opted-out repos skipped, so that the Sweep drafts only what's worth reading.
83. As a developer, I want Sessions judged not worth keeping recorded in a per-machine ledger, so that they aren't re-read every day.
84. As the Vault owner, I want any Dump body matching a common secret pattern refused by `write-dump`, swept or manual, so that credentials never land in the Vault.
85. As the Vault owner, I want a whole Sweep undoable as one Run, so that one command reverses it.
86. As a developer, I want the Sweep capped at 25 Sessions per run with the rest carried over, so that one run stays bounded.
87. As a developer, I want unreadable or changed log formats reported and retried rather than crashing the Sweep, so that a tool upgrade doesn't silently stop capture.
88. As a developer, I want a summary of every Sweep shown by the pointer hook and by `file`, and `brain-dump sweep --last` for the full report, so that I know what it did.
89. As a developer, I want `install.sh` to ask once whether to enable the daily timer and say how to turn it off, so that automation is opt-out and visible.
90. As a developer on two machines, I want overlapping Sweeps on one machine prevented by a lock, so that runs never collide.
91. As a developer, I want a manual `dump` to record the Session id and how far it reached, so that the Sweep doesn't draft the same Session again.

### Duplicate detection

92. As the Vault owner, I want an Item that nearly duplicates one already in the Vault or in another unfiled Dump marked `≈` with the existing text, so that I can drop it.
93. As the Vault owner, I want matched Items still filed unless I say `drop N` or `skip N`, so that detection only advises.
94. As the Vault owner, I want a near-duplicate never treated as Routine, so that the compact list can't hide it.
95. As the Vault owner, I want a match against an Item already done labelled `(done)`, so that I know whether the earlier one was acted on.

### Prompt evals

96. As a developer changing the `dump`, `chat-dump`, `file` or Sweep drafting prompt, I want to score it against committed fixtures, so that a regression is caught before it ships.
97. As a developer, I want deterministic assertions to decide pass or fail, so that the gate isn't flaky.
98. As a developer, I want each fixture run three times with all three required to pass, so that a fragile prompt doesn't pass on a lucky run.
99. As a developer, I want an advisory rubric grade printed beside the result, so that I see quality changes the assertions don't catch.
100. As a developer, I want `bun test` to fail when a prompt, its shared rules, its fixtures, its assertions or the pinned model changed without a fresh eval pass, so that evals can't be skipped by accident.
101. As a developer, I want fixtures to be synthetic, so that nothing private lands in a public repo.
102. As a developer, I want the `file` eval to fail if anything in the sandbox Vault is written, so that the eval can't cause the very harm it tests for.

### Repo changes

103. As a developer, I want one Vault layout module that defines the Inbox, `Inbox/Filed`, the Routes note, the Weekly Notes folder, the template path and the write allowlist, so that every command agrees on the Vault's shape.
104. As an agent, I want `list-notes` scoped to the write allowlist, so that Filing never proposes private notes.
105. As a developer, I want the Item rules in one shared prompt fragment used by `dump`, `chat-dump` and the Sweep, so that they can't drift apart.
106. As a chat-app user, I want `dump --paste` documented as the primary chat route, so that long chats are captured reliably.
107. As a developer, I want property tests on the append-only check, so that its guarantees hold across many generated edits, not just hand-picked cases.

## Implementation Decisions

Each decision gives the ticket that holds its full detail on the [v2 map](https://github.com/ChrisKalahiki/Brain-Dump/issues/29). Build order: the safety layer first (Vault layout module, write gateway, run store, undo, stale-plan hashes, guard), then everything that writes or reads through it.

### Vault layout module (new)
- One module defines the Vault's shape:
  - `Inbox/`
  - `Inbox/Filed/`
  - the Routes note `Inbox/Filing Routes.md`
  - the Weekly Notes folder and the Weekly Note template path
  - the **write allowlist** of folder trees, subfolders included: `Inbox`, `Research/Main Notes`, `Research/Weekly Meetings`, `Side Projects`, `Resources`
- Every command reads Vault locations from it.
- Widening the allowlist takes a code change and a re-run of `install.sh`. There is no config file or note for it, because Obsidian Sync skips dot-files ([Which Vault folders are curated…](https://github.com/ChrisKalahiki/Brain-Dump/issues/30), ADR 0004).
- `list-notes` returns only notes inside the allowlist.

### Write gateway (new; every Vault write goes through it)
Detail: [What exactly does the append-only check accept?](https://github.com/ChrisKalahiki/Brain-Dump/issues/31), ADR 0005.

**Modes:**
- **Create-new:** never overwrites.
- **Append to an existing note:** Curated Notes and the Routes note.
- **Dump checkbox-and-move.**
- **Revert:** used only by `undo`.

**Rules it enforces before anything is replaced:**
- the allowlist
- Inbox create-only for automation: nothing automated edits an existing Inbox file, `Inbox/Filed/` or the Routes note
- the 8-note plan-size limit: distinct notes written or created, not counting the plan's Dump or the Routes note; over 8 needs `confirmLarge: true`, which `file` sets only after a separate explicit yes
- the `expect` hashes
- the append-only check

**Append-only check:**
- A pure function over (original, next) that shares no code with the edit logic.
- For an existing note, every original line appears byte-for-byte and in order. New lines may go anywhere. Only an empty placeholder bullet (`- `, `- [ ]`, `- [ ] `) may vanish. Line endings must match.
- For a Dump, the line count is the same and only the planned Items' checkboxes change, from ` ` to `x` or `-`.
- It runs after all edits are staged, against each file re-read from disk at that moment.

**On any failure:**
- Nothing is written.
- The error names the note and the first lost or changed line, and says it is a `brain-dump` bug.
- There is no override.

**The Routes note** is written only through the gateway, as an append.

### Run store and `undo` (new)
Detail: [How do snapshots and undo work?](https://github.com/ChrisKalahiki/Brain-Dump/issues/32), ADR 0006.

**Runs:**
- A Run is one gateway commit: one `apply`, one `write-dump`, one Consolidation, one Sweep, or one undo.
- The store is per machine, outside the Vault, at `~/.local/state/brain-dump/runs/<run-id>/`.
- Run ids look like `YYYYMMDD-HHMMSS-xxxx`.
- Runs older than 90 days are pruned at the start of each new Run.

**Journal (`run.json`):**
- Run fields: id, time, command, label, host, Vault path, status (`pending` / `applied` / `undone`).
- Per file: Vault-relative path, operation (`create` / `append` / `checkbox` / `move {from,to}` / `delete`), and hashes before and after.
- `before/` holds a copy of each file that existed before the Run.
- The journal is fsynced as `pending` before any Vault file is replaced, then marked `applied`.

**`brain-dump runs`:** JSON listing the 20 latest Runs: id, time, command, label, file count, status.

**`brain-dump undo <run-id>`:**
- A dry run by default. `--confirm` applies it through Revert mode.
- All or nothing.
- A file is reverted only while it is byte-identical to what the Run left. Files the Run created are deleted; moved files are moved back. Files still at their before-hash are skipped, which keeps a crashed Run undoable.
- Refusals name every changed file, with the cause: "undo run `<id>` first" when a later local Run changed it, "changed outside Brain-Dump since `<time>`" otherwise.
- Also refused when the Run's Vault path isn't the current Vault.
- Undo is itself a Run, so undoing it works as redo.

**The `file` skill** gains an undo section: it resolves "undo the last Filing" to an id by reading `runs`, shows the dry run, and passes `--confirm` only after the user approves.

### Stale-plan hashes
Detail: [How does stale-plan detection carry hashes from list-notes to apply?](https://github.com/ChrisKalahiki/Brain-Dump/issues/35)

**Hashes:**
- A hash is the first 16 hex characters of the SHA-256 of a file's exact bytes, with no normalisation.
- Read commands add `hash`, taken from the same read the agent sees:
  - `list-notes`: per note
  - `list-dumps`: per Dump
  - `weekly-note` and `todo-groups`: for the Weekly Note
  - `show`: for the note

**Plans:**
- Filing Plans and `consolidate` plans gain a required `"expect": {"<path>": "<hash>"}` covering every existing file the plan writes: target notes, the Dump, and the Routes note when routes are appended.
- A plan that writes an existing file with no `expect` entry is refused.
- Any mismatch refuses the whole plan with `Filing Plan stale: <note> changed since it was read`, listing every changed file.
- `apply` returns `"hashes": {path: hash}` for every file it wrote, and `file` uses them for later plans in the same run.

**Recovery:**
- `file` re-reads, rebuilds the plan, and shows it headed `Re-planned: [[X]] changed since you last saw it`. It carries over the user's earlier replies where they still apply and waits for a fresh `ok`.
- `consolidate` refuses with `Consolidation plan stale: <note> changed since it was read`, and re-drafts.

### Vault guard: `brain-dump guard` (new command)
Detail: [How does the Vault guard hook decide what to block?](https://github.com/ChrisKalahiki/Brain-Dump/issues/34), [What can a Codex PreToolUse hook inspect and block?](https://github.com/ChrisKalahiki/Brain-Dump/issues/51)

**How it decides:**
- Reads hook JSON on stdin. The rules are tool-neutral: they decide on a path or on command text.
- **File tools:**
  - Covered: `Edit`, `Write`, `NotebookEdit`, `MultiEdit`, `Read`, `Grep`, `Glob`.
  - Paths come from `file_path`, `notebook_path` or `path`, falling back to `cwd`.
  - Both the path and the Vault root are realpath'd. A path that doesn't exist yet is resolved through its nearest existing parent.
  - A path inside the Vault is denied.
- **`Bash` / `PowerShell`:**
  - A call touches the Vault when its `cwd` is inside the Vault, or when its text names the Vault folder in any common spelling.
  - A call that touches the Vault is allowed only when the whole command is a single `brain-dump …` invocation: the first word is `brain-dump`, with at most one quoted heredoc and no `;`, `&&`, `||`, `|`, `$(`, backticks, or redirects outside the heredoc.
- **Stands down** when `CLAUDE_PROJECT_DIR` is inside the Vault.

**Deny message:** `Vault access goes through brain-dump only (recall, show, write-dump, file). Blocked: <tool> on <path | "Vault mention in command">.`

**Failure:**
- Internal errors deny only when the call plausibly touches the Vault, and allow otherwise.
- Indirect access (scripts, `cd "$V"`, globs, symlinks) is accepted residual risk. The gateway and undo are the safety net.

**Claude Code install:** `install.sh` asks once (default yes), then merges a user-level `PreToolUse` entry into `~/.claude/settings.json` without overwriting existing entries. The entry uses matcher `Edit|Write|NotebookEdit|MultiEdit|Read|Grep|Glob|Bash|PowerShell` and `timeout: 5`. The installer prints how to remove it.

**Codex adapter (best effort):**
- The same rules, plus parsing of `apply_patch` patch text: the `Add File`, `Delete File`, `Update File` and `Move to` marker lines, trimmed, with relative paths resolved against `cwd`. The text arrives either as `apply_patch`'s `command` or inside a Bash heredoc.
- Every deny emits a non-empty reason, because Codex fails open without one.
- Installed at `~/.codex/hooks.json` with a stable entry, so changing the script doesn't require re-trust. The installer tells the user to trust it once in `/hooks`.
- Known gaps, documented as best effort: `exec_command`'s `workdir` is hidden from the hook, and `write_stdin` is unhooked.

### Recall: `recall` skill, `brain-dump recall` and `brain-dump show` (new)
Detail: [Should agents read the Vault through a skill and recall command, or directly?](https://github.com/ChrisKalahiki/Brain-Dump/issues/37), [What does recall take and return…](https://github.com/ChrisKalahiki/Brain-Dump/issues/48), ADR 0007.

**Project identity:**
- The basename of the main worktree root (via the git common dir). Outside a repo, the directory name.
- Dump origins use the same rule.

**`recall`, exactly one mode per call:**
- `recall <terms…>`: case-insensitive term match over the Markdown, ranked by hits then recency. No index.
- `recall --project [name]`: newest first; defaults to the current repo's project.
- `recall --links "[[Note]]"`: returns `{"links":[{"note","line"}]}`.

**Result shape:**

```json
{"results": [{"note": "…", "kind": "decision|learning|todo", "text": "…", "why": "…",
  "unfiled": false, "dump": "Inbox/Filed/….md", "origin": "Session: …"}], "more": 7}
```

- `kind` is worked out from the bullet: a `Why:` line means decision, `#todo` means todo, anything else learning.
- For an unfiled Item, `note` is the Dump itself.
- Results are capped at 20.
- Scope is the allowlist. Dropped Items are excluded.

**`show <note>`:**
- Returns the latest Digest onward, or the whole note when it has no Digest.
- Capped at ~60k characters. `--full` returns the whole note with no cap.
- Includes `hash`.

**`recall` skill:**
- Description: "Look up what the Vault already holds about this project or a subject: past Decisions with their Rationale, Learnings, open Todos, and the Session each came from. Use when starting work on a project, before re-deciding something that may already have been decided, or when the user refers to earlier work ("what did we decide about…", "last time we…"). Not for anything that is in the repo itself."
- Implicit invocation is allowed in both tools (Codex: `allow_implicit_invocation: true`). The permission is `Bash(brain-dump:*)`.
- Agents never read the Vault natively, and it is never added to `additionalDirectories`.

### Pointer hook: `brain-dump pointer` (new command)
Detail: [What does recall take and return…](https://github.com/ChrisKalahiki/Brain-Dump/issues/48)

**Install:** `install.sh` merges one user-level `SessionStart` entry into both `~/.claude/settings.json` and `~/.codex/hooks.json`, never overwriting existing entries. The entry sets a 5s `timeout`.

**Mapping a repo to notes:**
- The project's Route target first.
- Then notes holding Items whose `From [[dump]]` backlink points to a Dump with this project in its origin, ranked by Item count.
- No fuzzy matching.

**Output:** up to three lines, each printed only when it has content. A Session with nothing to show gets no output.
- **Notes line:** at most 3 notes, plus this project's unfiled-Dump count and "use the recall skill for more".
- **`check` line:** `brain-dump: N Vault findings (run brain-dump check)`.
- **Sweep line:** only when the last Sweep ran within 24h and wrote something or hit a problem.

**Time budget:** a 1s internal deadline. The pointer lookup runs first, then `check` only if time remains. Anything that misses the deadline is skipped silently.

### `brain-dump check` (new command)
Detail: [What does check report, and at what thresholds?](https://github.com/ChrisKalahiki/Brain-Dump/issues/38)

**Behaviour:** read-only, scoped to the allowlist, thresholds are code constants, and findings can't be silenced.

**Findings:**

| Kind | Rule | Fix |
|---|---|---|
| Broken backlink | a `From [[dump]]` or `Filed [[…]]` link that doesn't resolve to a Dump | hand edit, or restore the Dump |
| Dead Route | a line in the Routes note that targets a missing note | edit the Routes note |
| Stale Dump | `- [ ]` Items more than 14 days past the filename date | `file`, or `drop N` |
| Stuck Dump | in `Inbox/` with no `- [ ]` left, or in `Inbox/Filed/` still holding `- [ ]` | re-run `file`, or move by hand |
| Oversized note | a Topic Note or Project Note (never a Weekly Note) with ≥ 40 backlinked Items since the latest Digest's `^digest-…` line, or in total when there is no Digest | `/consolidate [[note]]` |
| Duplicate Item | an exact match within one note after normalising case, whitespace, checkbox, `#todo` and the backlink line | remove by hand, or leave for the next Digest |
| Malformed Dump | frontmatter, origin line or sections can't be parsed | hand edit |

**Output:**
- Default text is one line per finding, grouped by kind: `<kind> · [[note]] · <detail> → <fix>`.
- `--json` gives `[{kind, note, detail, fix}]`.
- Exit codes: 0 clean, 1 findings, 2 error.

**Scheduling:** none of its own. `file` runs it first and shows a one-line summary; the pointer hook shows the count.

### Consolidation: `consolidate` skill and `brain-dump consolidate` (new)
Detail: [What shape does a Digest take…](https://github.com/ChrisKalahiki/Brain-Dump/issues/39), ADR 0008.

**Digest shape:**

```
> [!summary] Digest 10-10-26
> Supersedes [[#^digest-100126]] · 47 Items
> - Theme bullet … [[<dump>|dump 09-30-26]]
^digest-101026
```

- The callout is added at the note's end.
- A second Digest on the same day becomes `Digest 10-10-26 (2)` with ID `^digest-101026-2`.
- `Supersedes` appears only when an earlier Digest exists.
- 3–10 bullets grouped by theme. Decisions that still hold get a one-line Why. Open Todos aren't restated. Contradictions are flagged ("earlier X, later Y").
- Each bullet links to the Dumps its Items came from. Material drawn from hand-written text is marked `(hand-added)`.
- No frontmatter change.

**Coverage:**
- Cumulative: the previous Digest plus everything after it, or the whole note when there is none.
- The latest Digest is the last `> [!summary] Digest MM-DD-YY` callout, ended by its `^digest-MMDDYY` line.

**Trigger and plan:**
- `/consolidate [[note]]` reads the note through `show` and drafts the Digest.
- `brain-dump consolidate <note>` takes the plan on stdin, carrying the Digest text and `expect`. It applies the Digest as one append-only Run. Only the skill calls it.
- The plan is `{"expect", "bullets"}`: the skill drafts the 3–10 bullets, and the helper writes the title, `Supersedes` line, Item count and ID, so placement and same-day numbering can't drift. Without `--confirm` it prints the exact lines and the Digest ID and writes nothing, as `undo` does, so the skill shows the full text before `ok`. With `--confirm` the plan also carries that ID, and a Digest that would now get a different one (the date turned over) is refused as stale.
- Allowed on Topic Notes and Project Notes with at least 1 filed Item since the latest Digest. Weekly Notes are refused.
- Manual only, plus a one-line offer from `file` for notes its pre-run `check` flagged as oversized.
- The plan shows the target note, the Items covered, the Digest it supersedes, and the full text.
- Replies: `ok`, `edit` (reword the text directly, or give an instruction and re-draft), `cancel`.
- One note per Run, never Routine.

### Approval tiers (changes to the `file` skill and `apply`)
Detail: [How do approval tiers split a Filing Plan into routine and full?](https://github.com/ChrisKalahiki/Brain-Dump/issues/40)

**Which Items are routine:**
- A Routine Item's destination came from a note Route or a Todo Group Route, and that destination already exists. The link line is routine too.
- Anything NEW always goes in the full table.
- Near-duplicates (`≈`) are never routine.

**Layout:**
- The full table holds the non-routine Items.
- Below it, `Routine (N)` lists each routine Item's index, kind, excerpt, and `→ destination (via Route "<key>")`.
- When every Item is routine, the plan shows only that list and still waits for `ok`.

**Replies:**
- No new verbs. All replies act on routine Items too.
- A redirect or `edit` moves the Item to the full table on redisplay.

**Enforcement and limits:**
- Each routine Item carries `"route": "<key>"` in the plan JSON. `apply` verifies the Route exists and points at the Item's note or group, and refuses the whole plan if not.
- The 8-note limit is unchanged and counts routine notes.
- Still one plan and one `ok` per Dump.

### Sweep: `brain-dump sweep` (new command), timer, and `write-dump` changes
Detail: [How does the automated capture sweep find Sessions and draft Dumps into the Inbox?](https://github.com/ChrisKalahiki/Brain-Dump/issues/42), [Where does Claude Code store Session logs…](https://github.com/ChrisKalahiki/Brain-Dump/issues/41), ADR 0009.

**Trigger:**
- A daily per-machine OS timer at 04:00 local: a systemd user timer with `Persistent=true` on Linux, launchd on macOS.
- `install.sh` asks once (default yes) and prints how to disable it.
- A per-machine lock prevents overlapping runs.

**Candidate Sessions:**
- Sessions with records since the last successful Sweep, at most 28 days back, newest first.
- Capped at 25 Sessions per run (a constant). The rest carry over and are listed in the summary.
- Excluded:
  - subagent transcripts and Codex sub-agent threads
  - Sessions whose working directory is inside the Vault
  - Sessions active in the last 2 hours
  - Sessions with fewer than 3 user messages
  - Claude Code `.orphaned-` and `.superseded-` files
  - repos on an opt-out path list, a second setting in `~/.config/brain-dump/config`
  - Sessions covered by a Dump in `Inbox/` or `Inbox/Filed/`
  - Sessions in the skip ledger

**Readers, one per tool:**
- Extract only user text, assistant text, timestamps, `cwd` and branch. Unknown record types are ignored.
- Claude Code rows are de-duplicated by `uuid`. Codex user and assistant text comes from message events, never `replacement_history` or `response_item` copies: `event_msg`/`user_message` and `agent_message` before Codex 0.147, `event_msg`/`item_completed` with a `UserMessage` or `AgentMessage` item since. Codex `cwd` and branch come from `session_meta`.
- A Codex sub-agent Session is one whose `session_meta` has `thread_source: "subagent"`, a `parent_thread_id`, or a `source.subagent`. A reverted Codex Session, which goes on in a new rollout under the same thread id, is drafted from its newest rollout only.
- `.jsonl.zst` files are decompressed with Bun's zstd; one that won't decompress is reported as unreadable.
- A file with no user messages is reported as unreadable and retried next run.
- A transcript that starts with `compact_boundary` is drafted from what remains, and its origin line notes the earlier material is missing.
- Text is capped at ~150k characters by keeping the head and tail; the origin line then says `(truncated)`.
- A resumed Session is drafted only from records after its Dump's `through`.

**Drafting:**
- One fresh `claude -p --no-session-persistence` per Session, with no tools. The model is a helper constant.
- The prompt is the shared Item rules plus the output contract: a slug and a Dump body on stdout.
- The helper writes the result through `write-dump`.
- On agent failure (auth, rate limit, bad output) the Sweep stops, and unreached Sessions are retried next run. A body that fails validation is reported and skipped.
- No Items means no Dump, and the Session goes in the skip ledger, which sits next to the run store.

**`write-dump` changes, for swept and manual Dumps alike:**
- Frontmatter gains `session: <id>` and `through: <timestamp of the last record covered>`.
- A manual `dump` gets the id from `CLAUDE_CODE_SESSION_ID` or `CODEX_THREAD_ID`, which `write-dump` reads from its own environment for the matching tool, since the guard refuses `${…}` in a command. A focused `dump` passes `--session ""` so the Sweep still drafts the rest of the Session. `through` defaults to the Dump's time.
- Swept Dumps get the tag `dump/swept` and the origin line `Session: <tool> (swept) · …`.
- Every body is refused when it matches common secret patterns: `sk-…`, `ghp_…`, AWS keys, PEM headers, `password=`.

**Runs and reporting:**
- One Sweep is one Run.
- The summary goes in the run store and lists:
  - Dumps written
  - Sessions skipped as not worth keeping
  - files reported as unreadable
  - drafts refused by the secrets check
  - carried-over Sessions
  - errors
- It is shown by the pointer hook and at the start of `file`. `sweep --last` prints the full report.

### Duplicate detection (changes to `list-dumps` and the `file` skill)
Detail: [How does Filing detect near-duplicate Items…](https://github.com/ChrisKalahiki/Brain-Dump/issues/52)

**Matching:**
- Text is normalised as `check` does, stopwords are dropped, and word sets are compared.
- A match needs Jaccard ≥ 0.7 (a constant), with at least 3 words on each side.
- Each open Item is compared against the allowlist's Items and the other Inbox Dumps' Items. Done Items are included and labelled; dropped Items are excluded.
- From other Dumps only open Items count: a Dump's `[x]` means filed, and its filed copy is matched in its curated note.
- `list-dumps` adds `similar: {note, text, score, done}` to each Item: the best match only, or absent.
- `apply` refuses a plan that claims a Route for a near-duplicate, so it can't be shown as routine.

**In the plan:**
- A matched row is marked `≈`.
- Below the table, one line per match: `≈ N ~ [[note]]: "<existing text>"`, with `(unfiled)` or `(done)` where they apply.
- The Item still files by default; only the user's `drop N` or `skip N` changes that.
- `check` stays exact.

### Prompt evals (new runner, outside `bun test`)
Detail: [How are Brain-Dump's skill prompts evaluated when they change?](https://github.com/ChrisKalahiki/Brain-Dump/issues/53)

**What gets evals:**
- Evaluated: the Sweep's drafting step, run through the helper's own call and parsing; `dump`; `chat-dump`; and `file` up to the Filing Plan.
- Hand checks only: `consolidate`, whether `recall` triggers when it should, and `chat-dump` in ChatGPT and Gemini.

**Fixtures:**
- Synthetic and committed: extracted Session text and pasted chats.
- One fixture over the cap, one with a planted fake secret.
- `file` uses a fixture Vault with notes, a Route and a Todo Group, plus one case per plan feature: Routine, NEW note, NEW group, `≈`, link line.

**Scoring:**
- Deterministic assertions gate:
  - the body passes `write-dump` validation
  - Item kinds and counts fall in a range
  - must-mention and must-not-contain checks
  - for `file`, the destination and marks per Item
- 3 runs per fixture, all must pass. `--runs N` overrides.
- A per-eval rubric, graded 1–5 by the pinned model, is printed and never gates.

**The `file` eval:**
- `claude -p "/file"` with only `Bash(brain-dump:*)`, against a sandbox Vault.
- No reply is sent.
- The plan table is parsed. Any change to the Vault fails the run.

**Running and recording:**
- `bun run eval [name]` writes a passed-record: each eval's input hash, date and model.
- Each eval declares its inputs: prompt files, shared rules, fixtures, assertions and the model constant.
- A `bun test` check fails when an input changed without a fresh pass.
- No CI in v2.

### Other repo changes
- The Item rules move to one shared prompt fragment, included by `dump` and the Sweep and built into `chat-dump`'s paste text.
- `dump --paste` becomes the documented primary chat route. `dump <chat URL>` stays as a convenience.
- `install.sh` now asks before each config change (guard, pointer, timer) and merges hook entries without overwriting. This reverses v1's "edits no config".
- New skills: `recall` (both tools) and `consolidate` (Claude Code).

## Testing Decisions

**What makes a good test:**
- It drives the real `brain-dump` CLI as a user or skill would, and asserts only what comes out: stdout, stderr, exit code, and the resulting Vault and run-store files.
- No test reaches into module internals. Tests survive refactors.
- The style follows the existing tests: `#given / #when / #then`, with one combined `toEqual` over the outputs that matter.

**Seam 1, the main one: the CLI against a sandbox.**
- Reuse the existing harness, which gives a temporary `HOME` holding the Vault, config, run store and Session logs.
- Prior art: the existing `apply`, `write-dump`, `list-dumps` and `todo-groups` tests.
- Tested through this seam:
  - the write gateway (allowlist, Inbox create-only, 8-note limit and `confirmLarge`, append-only refusals and their messages, all-or-nothing)
  - `runs` and `undo` (dry run, `--confirm`, refusals for changed files and wrong Vault, redo, crashed `pending` Runs, 90-day pruning)
  - `expect` refusal and the returned `hashes`
  - `guard` (hook JSON on stdin, then exit code and reason, for each tool shape, Bash forms, realpath and symlink cases, stand-down, error handling; Codex `apply_patch` and heredoc payloads)
  - `recall`, `show`, `pointer` (output, empty case, deadline skip)
  - `check` (each finding kind, text and JSON, exit codes)
  - `consolidate` (Digest placement, IDs, same-day suffix, Weekly Note refusal)
  - Route verification for routine Items
  - `similar` in `list-dumps`
  - `write-dump`'s secret refusal and `session`/`through` frontmatter
  - `sweep`, using fixture Claude Code and Codex JSONL placed under the sandbox `HOME`: selection rules, ledger, carry-over, `through` resumption, truncation, `.zst`, unreadable files, one Run per Sweep, `--last`
- **Three new overrides** at the process boundary, honoured by the CLI:
  - A **clock override**: an environment variable read as "now", for ages, windows, retention and Run ids.
  - A **drafting-agent override**: the command run in place of `claude -p`, so tests use a stub script that prints a canned slug and body, prints junk, or exits non-zero.
  - A **pointer deadline override** (`BRAIN_DUMP_POINTER_DEADLINE_MS`): the pointer's deadline in milliseconds, so a test can force a miss. It is measured from process start, separate from the clock override. It can only force a miss of every line; a run that ends partway (some lines printed, later ones skipped) is left to review.

**Seam 2: property tests on the append-only check, in process.**
- The check is a pure function (ADR 0005), so generated cases call it directly. Spawning the CLI per case is too slow.
- Properties to cover:
  - every append-only edit passes
  - any deletion or change of a non-placeholder line fails
  - reordering fails
  - removing a placeholder passes
  - a line-ending change fails
- This is the only test below the CLI.

**Seam 3: prompt evals.**
- `bun run eval` runs against the real model, by hand.
- A plain `bun test` check guards that every eval's recorded input hash is current.

**Not tested automatically:**
- the OS timer units
- `install.sh`'s config merging, which is checked by hand on both machines and listed below
- Codex `/hooks` trust

## Out of Scope

- A dashboard, always-on Slack or email ingestion, and a vector database or embeddings.
- Rewriting or removing existing curated text, including rewrite-style Consolidation (ADR 0003).
- A git repo over the Vault. The user may run one; Brain-Dump neither requires nor manages it.
- Configurable thresholds, or silencing `check` findings.
- `ok all` across Dumps, and silently applied Routine Items.
- Fuzzy duplicate matching in `check`.
- Cross-machine undo, and cross-machine Sweep coordination.
- CI for evals, and automated evals of `consolidate`, `recall` triggering, or non-Claude chat apps.
- A "recent activity" recall mode.
- `file` and `consolidate` in Codex.
- Windows and mobile, and a second Vault (unchanged from v1).
